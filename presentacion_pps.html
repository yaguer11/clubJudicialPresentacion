Bloque 3 · Autenticación

Base de Datos: Autenticación y Roles

La cuenta para entrar, separada de la ficha del socio

EG · Base de Datos
  1. La cuenta para entrar Cada persona que usa el sistema tiene una fila en Usuario: nombre de usuario, contraseña cifrada y si la cuenta está activa. Acá no hay datos personales.
  2. La ficha del socio DNI, legajo, tipo de socio y datos de contacto viven en Socio, enlazada a su Usuario. Así el personal administrativo puede tener cuenta sin figurar en el padrón.
  3. El catálogo de roles Rol es una lista cerrada de permisos del backoffice (SUPERADMIN, ADMIN_ALQUILER…). Nadie puede inventar un rol escribiéndolo a mano.
  4. Varios roles por persona Usuario_Rol es la tabla intermedia N:M: una misma persona puede ser de Alquileres y de Prensa. Su clave doble (ID_Usuario, ID_Rol) evita repetir un rol.
  5. Reglas que cuida el motor Contraseñas solo con hash Bcrypt; Username, DNI y Legajo UNIQUE para que no haya duplicados; y ON DELETE CASCADE: si se borra una cuenta, se van sus roles y su ficha sin dejar datos huérfanos.

Bloque 3 · Autenticación

Backend: API de Autenticación

Esquema de doble token JWT y autorización RBAC

GM · Backend
  1. Login El socio ingresa con DNI y contraseña; el personal usa su propio endpoint /login-admin.
  2. Verificación con Bcrypt La API busca el hash del usuario y lo compara con bcrypt.compare(): nunca se guarda ni se compara texto plano.
  3. Doble token JWT Si coincide, emite un access token de 15 minutos y un refresh token de 7 días.
  4. Request protegido Cada pedido viaja con Authorization: Bearer. Se verifica el JWT y los middlewares de rol (isAdmin, canManageAlquileres…) responden 403 si el rol no alcanza.
  5. Renovación silenciosa Cuando el access token vence, la API responde 401 (falla de autenticación, no de rol) y el cliente usa el refresh token para obtener uno nuevo, sin volver a loguearse.

Bloque 4 · Padrón Social

Base de Datos: Socios y Membresía

Titular, grupo familiar y cambios que siempre pasan por secretaría

EG · Base de Datos
  1. La ficha del titular Socio guarda los datos civiles. DNI y Legajo son únicos, Tipo indica si es común, adherente o vitalicio, y Aprobado arranca en falso: el socio nace pendiente hasta que secretaría lo aprueba.
  2. El grupo familiar Cada familiar es una fila en Miembro_Familiar con su DNI, fecha de nacimiento y foto del DNI en Cloudinary. No hay columnas fijas tipo Hijo1, Hijo2: un socio puede tener 0 o 10 familiares.
  3. Parentesco como catálogo CONYUGE, HIJO, HIJA, PADRE, MADRE… se cargan una sola vez y se referencian por ID, así no aparecen variantes mal escritas. RESTRICT impide borrar un parentesco que está en uso.
  4. Cambios de datos auditados El socio no edita sus datos sensibles directamente: crea una Solicitud_Cambio_Datos con los valores nuevos. Cuando secretaría la aprueba, se aplica y queda registrado quién y cuándo.
  5. Altas y bajas de familiares Lo mismo para la familia: Solicitud_Cambio_Familiar indica si es ALTA, BAJA o MODIFICACION y espera la aprobación de secretaría.
  6. Búsqueda rápida Índices FULLTEXT sobre nombre, apellido y email del socio, y nombre y apellido de los familiares: el buscador del panel encuentra resultados sin recorrer la tabla entera.

Bloque 5 · Deportes & Alquileres

Base de Datos: Espacios y Alquileres

Tarifas, turnos, accesorios y reservas que se liberan solas

EG · Base de Datos
  1. El espacio y sus reglas Espacio guarda el precio para socios y no socios, la seña mínima, el seguro (porcentaje o monto fijo) y con cuántos meses de anticipación se puede reservar.
  2. Precio según el día Espacio_Precio_Dia permite cobrar distinto un sábado que un martes. Su clave es el espacio más el día de la semana, así cada día tiene una sola tarifa.
  3. Las franjas horarias Horario_Espacio define los turnos (día, hora de inicio y fin). Un UNIQUE impide cargar dos veces la misma franja y un CHECK exige que inicio y fin sean distintos.
  4. Accesorios con stock La relación N:M Espacio_Accesorio dice qué accesorios ofrece cada espacio; Accesorio lleva el stock total y el disponible.
  5. La reserva Alquiler guarda fecha, total, saldo, seguro y estado. Si reserva un invitado, se guardan sus datos de contacto y un TokenSeguimiento de 64 caracteres para que siga su reserva sin crear cuenta.
  6. Reserva y turno, unidos Alquiler_Espacio conecta cada reserva con la franja que ocupa. La API valida la disponibilidad dentro de una transacción para que dos personas no se queden con el mismo turno.
  7. Liberación automática FechaExpiracion marca hasta cuándo se puede pagar la seña (1 hora para socios, 24 hs para un invitado aprobado). Un job que corre cada minuto cancela las vencidas y libera el horario.

Backend: API de Alquileres y Turnos

Concurrencia atómica, token de invitado y cancelaciones

GM · Backend
  1. Disponibilidad El cliente consulta los horarios libres de un espacio antes de reservar.
  2. Dos pedidos al mismo turno Un socio y un invitado confirman la cancha de pádel del sábado 20:00 casi en el mismo instante.
  3. Transacción atómica La verificación del solapamiento y el alta de la reserva ocurren dentro de una misma transacción (connection.beginTransaction()): nadie puede colarse en el medio.
  4. Cero solapamientos El primero queda confirmado; el segundo recibe «horario ocupado» y su transacción se revierte.
  5. Seña con vencimiento El socio tiene 1 hora para pagar la seña (24 hs un invitado aprobado). Si no paga, el cron expireAlquileres cancela la reserva y libera el horario.
  6. Reserva como invitado Un no socio reserva sin crear cuenta: recibe por email un TokenSeguimiento único para consultar y pagar su turno en /alquiler-guest/:token.
  7. Cancelación La reserva pasa a CANCELADO y el horario se libera al instante. No hay reembolsos automáticos: con menos de 48 hs la seña queda retenida; el seguro de depósito sí se devuelve tras el evento.

Base de Datos: Cuotas, Pagos y Cajas

Cuotas mensuales, pagos parciales y una caja que no se descuadra

EG · Base de Datos
  1. Una cuota por mes Cuota tiene un registro por socio y período (ej. 2026-05). El UNIQUE (ID_Socio, Periodo) impide generar dos veces la cuota del mismo mes.
  2. Pagos parciales PorcentajePagado va de 0 a 1, controlado con un CHECK. Así una cuota puede quedar PENDIENTE, PARCIAL o PAGADO sin errores de redondeo.
  3. Un pago, varias cuotas Pago registra el monto, la fecha y el método (MercadoPago, transferencia, efectivo o planilla). Pago_Cuota reparte ese pago entre las cuotas que salda.
  4. La deuda en una sola fila Deuda_Socio guarda la cantidad de cuotas adeudadas ya calculada: es una desnormalización a propósito. Se actualiza en la misma transacción de cada pago, así la lectura es instantánea y siempre coincide.
  5. El libro de caja Cada pago aprobado genera un Caja_Movimiento. El UNIQUE sobre ID_Pago impide registrarlo dos veces y el CHECK exige montos mayores a cero.
  6. Planillas reversibles Los pagos que llegan en la planilla de sueldos quedan atados a su Importacion_Planilla. Mientras no esté confirmada, el rollback deshace en una transacción esos pagos, las cuotas que saldaron y la deuda de cada socio.

Bloque 6 · Finanzas & Cuotas

Backend: MercadoPago y Planillas con Rollback

Checkout Pro, Webhooks IPN y procesamiento XLSX seguro

GM · Backend
  1. Crear preferencia La API calcula cuántas cuotas cubre el monto según el valor vigente, crea la preferencia con el SDK de MercadoPago y registra el Pago en PENDIENTE con su preferenceId.
  2. Checkout Pro El socio paga dentro de MercadoPago, sin ingresar datos de tarjeta en nuestro sistema, y vuelve por las back_urls: /pagos/success, /failure o /pending.
  3. Webhook IPN MercadoPago notifica a la API; se valida el paymentId contra MP y, en una transacción con rollback, se descuentan cuotas en Deuda_Socio, se registra el Pago y el ingreso en Caja_Movimiento.
  4. Idempotencia Si la misma notificación llega dos veces, el PaymentID ya registrado hace que se ignore: nunca se cobra ni imputa dos veces.
  5. Importar planilla Tesorería sube el Excel de retenciones de haberes; la librería xlsx lee las columnas obligatorias CUIT/CUIL e IMPORTE.
  6. Imputar por CUIL Cada fila se cruza por CUIL, el identificador con el que liquida el Poder Judicial, y descuenta cuotas solo a socios de tipo COMUN dentro de una transacción.
  7. Se detecta un error Un importe cargado mal en la planilla deja deudas incorrectas.
  8. Rollback en un clic La importación se deshace de forma transaccional y se restauran las deudas anteriores.
